01产品定位与目标

1.1 一句话定位

以「双向意愿」为核心机制的交友产品：用户先把自己的画像和择偶偏好讲清楚，系统按偏好推卡，只有双方都 Like 才建立会话——把「被拒绝的成本」降到零，让主动表达变得没有负担。

产品名

相悦 / Mutual。中文出自「两情相悦」——中文里形容「双方互相喜欢」最准确的一个词，正好对应产品「双向 Like 才配对」的核心机制；英文 Mutual 语义完全对应。两字好记好听，气质上比传统婚恋站年轻、比泛社交产品认真，与「重资料 + 轻交互」的定位一致。

1.2 与竞品的差异点

机制常见做法本产品做法
匹配门槛单向 Like 即可发消息（骚扰成本低）双向 Like 才开聊天，从机制上杜绝单向骚扰
信息结构只有「我是谁」本人画像 + 伴侣画像两套，明确「我要什么」，降低无效匹配
发现方式只有推荐流推荐流（划卡）+ 恋爱广场（条件检索）双通道，两者共用每日 Like 额度
社交线索不告诉谁看过你Like & Visit 呈现谁对你表达了兴趣

1.3 产品目标

  • G1 Onboarding 走完率：五步全部强制（不可跳过），目标下调为 ≥ 55%，并单独跟踪每一步的流失率（详见 3.3）。
  • G2 双向匹配有效：配对后的首条消息发送率 ≥ 60%（配了不说话等于没配）。
  • G3 划卡有效率：每日额度内（10 次 Like）的 Like 率落在合理区间——用户浏览的卡片数可以很多，但主动表达的应该少而准。若用户每天把 10 次额度全用光，说明推荐宽度合适；若用不完，说明推荐太窄或资料不足。
  • G4 生态健康：男女双方的「被 Like 分布」不过分倾斜，头部用户不虹吸全部曝光。

1.4 非目标（本期不做）

  • 不做语音/视频通话（聊天先做图文）。
  • 不做付费会员体系（本期所有功能免费，但字段设计为将来可挂付费墙，见 20 章）。
  • 不做实名认证的强校验（本期只做手机号注册，实名与活体检测列为 P1，见 14 章）。
  • 不做动态/朋友圈内容流（只有恋爱广场这种「人」的检索，不做「内容」流）。

3.3 Onboarding 五步（全部必填，均不可跳过）

步骤内容完成标准（达到才可进入下一步）为什么放在这个位置
1本人画像所有必填字段填写完成 + 头像已上传最基础的「我是谁」，决定后续推荐
2兴趣爱好 ×3（含文字）恰好 3 个，且每个都填写文字介绍（10–200 字）画像之后，趁用户还在投入状态
3关于我填写 20–500 字承接兴趣，自然过渡到文字自述
4伴侣画像所有必填字段填写完成先讲清自己，再讲要求（心理顺序）
5期待的那个他/她填写 20–500 字；完成后立即进入划卡收尾，文字表达
「不可跳过」的确切含义

不可跳过 = 不完成本步就无法进入下一步，也无法进入划卡 / 广场 / 聊天。但允许中途退出、下次登录从断点续填——这两件事不矛盾：前者保证资料的完整性，后者防止用户填到一半被迫放弃而丢失数据。断网、切后台、主动退出都必须能恢复现场。

需要区分：「步骤不可跳过」不等于「该步骤内所有字段都必填」。步骤 1 中的「学校」「公司名字」在原需求里就明确标注为选填，本次保持不变；步骤 4 中的「车 / 房」偏好同理。不可跳过约束的是「这一步必须走」，不是「每一格都必须填」。

代价：走完率会下降，必须配套缓解手段

五步全部强制，且包含三段文字（3 个兴趣介绍 + 关于我 + 期待的他/她），这是相当重的填写负担。原定的「走完率 ≥ 70%」目标需要下调，建议改为 ≥ 55%，并单独跟踪每一步的流失率——这样才能看出究竟是哪一步在劝退用户。

缓解手段（建议全部做）：①显示进度「3 / 5」与预估剩余时间；②每步完成给即时正向反馈；③文字字段给对照示例而非空白输入框；④支持保存草稿、随时退出续填；⑤对中途放弃的用户做召回（推送 / 短信），从断点继续。

04账号体系（注册 / 登录）

按需求：手机号 + 密码即可注册并登录，本期不做验证码。这一章落到具体规则，并在 4.4 指出它带来的三个必须正面处理的后果。

4.1 注册

项目规则
手机号11 位中国大陆手机号，正则 ^1[3-9]\d{9}$；全局唯一，已被注册则提示「该手机号已注册，请直接登录」并跳到登录页
密码长度 8–20；至少包含字母与数字；不允许纯数字、纯字母、连续或重复字符（12345678 / aaaaaaaa）；前后端双重校验
确认密码二次输入需一致
注册后状态registered，强制进入 Onboarding，未完成不得进入划卡/广场
服务协议必须勾选《用户协议》《隐私政策》（未勾选时按钮置灰）

密码存储：服务端使用 bcrypt（cost ≥ 12）或 argon2id 加盐哈希，严禁明文或可逆加密；哈希值与盐独立存储，日志中不得打印任何密码字段。

4.2 登录

项目规则
凭证手机号 + 密码
会话登录成功签发 JWT（access token 2 小时）+ refresh token（30 天，可撤销）；移动端持久化，Web 端用 httpOnly cookie
失败提示统一提示「手机号或密码不正确」，不区分「手机号不存在」与「密码错误」（防账号枚举）
限流同一手机号连续失败 5 次锁 15 分钟；同一 IP 每分钟 > 20 次登录请求则拒绝

4.3 账号状态机

已注册 REGISTERED→ 完成Onboarding → 正常 ACTIVE⇄ 冻结 FROZEN 封禁 BANNED 注销 DELETED
  • REGISTERED：可登录，但只能做 Onboarding，划卡/广场/聊天全部拦截并引导补全。
  • ACTIVE：完整功能。
  • FROZEN：被举报待审核期间，可登录但不可划卡、不可发消息（防止继续作恶）。
  • BANNED：封禁，登录即提示违规原因与申诉入口。
  • DELETED：注销。资料即时隐藏，30 天冷静期后可彻底匿名化。
不做验证码：三个必须正面处理的后果

1. 无法找回密码。没有验证码，用户忘记密码就等于账号作废。本期至少要给一条出路：「忘记密码」引导联系客服人工核验，并在数据库保留账号可迁移的痕迹。或者把「注册/找回时的短信验证码」列为 P1 首个补齐项。

2. 无法防止手机号被他人抢注。任何人拿到你的手机号（甚至只是猜到一个号段）就能注册。这会直接导致：用户想注册时发现「已被注册」，体验极差且无解。建议至少加一道「注册后不可用于找回」的兜底，或对连续注册的同一设备/IP 做风控。

3. 机器注册刷号零成本。没有验证码，脚本可以批量注册。必须在应用层补：设备指纹 + 单设备注册上限 + IP 频率限制 + 新账号行为限制（见 14 章）。

4.4 本期风控替代方案（在无验证码前提下）

手段规则
设备指纹客户端上报设备 ID + 机型 + 系统版本，同一设备注册上限 3 个账号 / 月
IP 限流同一 IP 每日注册上限 10 个；触发后要求人机校验（图形点选）
手机号归属校验校验号段合法性 + 运营商前缀，拒绝虚拟号段与明显伪造的号码
新号行为限制注册 24 小时内：不可发起聊天、不可上传相册（只能有头像），Like 上限降为每日 5 次
异常模式识别同一设备多账号、资料高度雷同、短时间大量 Like 同一批人 → 打标待审

05Onboarding · 本人画像

字段清单与规则逐条落到下表。「必填」是能否进入划卡的硬门槛；选填字段会体现在资料完整度上，但不阻断流程。

需求缺口 · 必须补的两个字段

1. 性别（缺失）。你的列表里没有「性别」，但伴侣画像和「期待的那个他/她」的表述都依赖它。没有性别，推荐引擎无法做同/异性匹配。必须补 性别（男 / 女）。已确认本产品只做异性匹配，因此不需要「期望对方性别」字段——系统固定为「男用户只看到女用户，反之亦然」。

2. 昵称（缺失）。划卡卡片、聊天列表、广场列表都需要一个展示名。手机号不能当展示名（隐私），必须有昵称字段（2–12 字符，允许中英文数字，敏感词过滤）。

已确认：只做异性匹配

性别是硬过滤的第一道闸门：推荐、广场检索、Like & Visit 全部只呈现异性。这带来两个简化：①不需要「期望对方性别」字段，也不需要处理复杂的性取向建模；②性别在注册后永久锁定（不允许自助修改），因为一旦可改，用户可通过改性别进入异性卡池，造成骚扰与数据污染。

5.2 通行门槛与资料完整度（两个不同的概念）

因为五步已全部强制，这两个概念必须拆开——否则「完整度」会失去意义（人人都一样高）。

概念性质作用
通行门槛二值（过 / 不过） Onboarding 五步的必填项与三段文字是否齐备。不齐备则拦截划卡、广场、聊天，只放行「继续填写」。
资料完整度0–100 分 含选填项与相册在内的填充率。只影响推荐曝光权重，不阻断任何功能。

完整度构成

完成 Onboarding 时完整度必然已达 85 分；后续的提升全部来自选填项与相册：

构成分值说明
Onboarding 五步必填项85走完五步即拿满，人人相同
选填项（学校 / 公司名字）5填写加分
相册10≥ 3 张拿满；照片越多，被划卡时的可信度越高

用途：完整度高的人在推荐排序中加权（同等条件下优先曝光）。因为 85 分是人人都有，真正拉开差距的是相册与选填项——这也是个人中心里引导用户「补充照片」的价值所在。

7.2 偏好是「权重」不是「门槛」——这一条决定产品生死

如果所有偏好都当硬过滤条件，用户会没有卡可划

假设一个用户选了：身高 175–185、只接受 3 个省的家乡、收入 30 万以上、硕士以上、不接受抽烟、希望有房有车、接受丁克。把这一串全部当 AND 条件去过滤，符合的人可能是百人量级甚至更少——在早期用户池里直接归零，用户打开就是「今日无推荐」。

正确做法：把偏好分成两层。

层级字段处理方式
硬过滤（不满足则完全不推） 性别、年龄、现居地距离（超出最大半径）、账号状态（封禁/已注销/已拉黑） 这些是「物理不可行」或「安全底线」，必须硬过滤
软加权（不满足则降权，仍可能出现） 身高范围、家乡、抽烟、喝酒、收入、学历、独生、车、房、丁克 每一项算一个匹配分，总分决定排序；允许少量「不完全符合」的卡出现在后面位置

补充机制：如果软加权后仍不够 10 张卡，逐步放宽软条件（先放宽收入与资产类，最后放宽地域类），并在卡片上标注「部分条件不符」让用户知情。「今日无推荐」是不可接受的终态。

7.3 双向匹配的计算

推荐时需同时看两个方向：

  • 正向：A 的伴侣画像 vs B 的本人画像。
  • 反向：B 的伴侣画像 vs A 的本人画像。反向也匹配的人，应该被排到更前面——因为你们互相满足，配对成功率显著更高。

最终分数示例：score = 0.6 × 正向匹配分 + 0.4 × 反向匹配分 + 活跃度分 + 完整度分 − 重复曝光惩罚。

8.4 曝光公平性（容易被忽略但决定生态）

马太效应会杀死交友产品

如果完全按匹配分排序，结果必然是：少数高吸引力用户获得绝大部分 Like，其余用户几乎无人问津 → 大量用户长期零配对 → 流失 → 卡池变小 → 剩下的人体验更差。

必须引入曝光均衡：记录每个用户近 7 天的曝光量与被 Like 率，对曝光不足的用户在推荐排序中加权；对已获得大量曝光的用户做限流。同时设置冷启动曝光保护：新用户注册后 72 小时内保证最低曝光量（如至少出现在 50 人的卡池中）。

这样设计的好处是逻辑统一、约束有效：不会出现「绕开划卡在广场无限 Like」的漏洞，也避免了大量「不看资料随手点」的低质量 Like。

对实现的要求：额度是一个全局单一计数池，无论 Like 来自哪个入口（划卡 / 广场 / 回 Like），都从同一个计数器扣减，且扣减必须与 Like 动作在同一事务内完成（防并发超额）。每个 Like 记录 source 字段（card / plaza / likes_me），便于事后分析用户把额度花在了哪里。

你确认了「回 Like 也消耗额度」。按此实现会产生一个可预期的现象，我如实写在这里：

「谁喜欢我」会变成一个清不完的队列。假设一位女用户当天收到 30 个 Like（在真实产品里并不罕见），但她的额度只有 10 次——她最多只能回应其中 10 人，剩下 20 人她「看得见却回不了」。而列表是按时间倒序的，新 Like 不断压进来，越早喜欢她的人越容易被永久积压。

直接后果：①该页面的转化率被人为压到 10/30 ≈ 33%，而它本来是配对率最高的入口；②男性用户的 Like 大量石沉大海，打击主动表达意愿（男性是 Like 的主要发起方）；③用户会感到「明明有人喜欢我，我却回不了」的挫败。

如果这是有意的稀缺设计（逼迫用户精挑细选、为将来付费埋点），那没有问题，只需在 UI 上把「今日还可喜欢 10 人」说清楚，避免用户误解为系统故障。如果不是有意的，建议考虑三个缓解方向：①回 Like 不消耗额度（最直接）；②仅「谁喜欢我」页面的回 Like 不消耗，广场与划卡照常消耗；③对收到 Like 远超额度的用户自动扩容。

「谁喜欢我」是产品最有价值的页面

它把「被动等待」变成「主动选择」——用户在这里的决策成本最低（对方已经喜欢我了，回 Like 的成功率是 100%）。这个页面应该在 Tab 上有最强的视觉引导（未读数角标），它是提升配对率最直接的杠杆。同时它天然是未来的付费点（见 20 章）。

12.1 会话创建

14安全、风控与合规

这一章是我补充的，不在你原始需求里

你的功能列表里没有提到审核、举报、拉黑、实名、未成年人保护。对一个带照片、带私聊、面向陌生人的社交产品，这些不是「锦上添花」，而是上线的前置条件——缺了它们，产品上线后会在很短的时间内被违规内容与诈骗占据。以下是我建议的最小集合，请在 20 章确认哪些进本期。

14.2 举报与拉黑 建议补充

  • 举报入口：主页、卡片详情、聊天会话内均需常驻。
  • 举报类型：色情低俗 / 虚假信息 / 骚扰辱骂 / 诈骗 / 推销 / 未成年 / 其他。

14.3 未成年人保护 建议补充（合规硬要求）

  • 注册时通过出生年月日强制校验，未满 18 岁拒绝注册。

  • 补偿手段（低成本、本期可做）：举报类型中单列「未成年 / 年龄不实」，命中后最高优先级人工处置；同一账号频繁修改生日触发风控标记。
  • 后续 若合规要求或风险上升，再引入身份证核验（成本与体验的权衡，本期不做）。

14.4 诈骗与风险提示 建议补充

  • 高风险话术识别：投资理财、博彩、代付、刷单、借款、索要红包等 → 实时弹出风险提示。

  • 反诈教育：在会话首次建立时展示一条简短的安全提示（不涉及转账、不点击外部链接）。

14.5 数据与隐私合规

  • 手机号、身份证等敏感信息加密存储，展示时脱敏。
  • 位置信息只存粗粒度的 geohash（5 位，约 5km 精度），不落库精确经纬度；距离由 geohash 中心点估算，并以区间形式展示（如「3–5 km」），不给精确距离。原始定位用完即弃，不倒卖给第三方。
  • 提供账号注销入口，注销后 30 天冷静期内可恢复，之后彻底匿名化。

共用同一份额度池。划卡、广场、回 Like 三者的 Like 全部从同一个计数器扣减；浏览与筛选不消耗。详见 10.3。
Q3 「谁喜欢我」是否免费可见
免费可见，不做付费墙。但同时不向对方推送通知（单向 Like 静默记入列表）。字段与接口预留将来改为付费的能力，本期不实现。详见 9.3。
Q4 回 Like 是否消耗额度
消耗，与划卡、广场共用同一份额度池。注意其连带后果（「谁喜欢我」队列清不完），已写在 11.2 的警示中。
Q5 是否支持同性匹配
只做异性匹配。性别为第一道硬过滤；无需「期望对方性别」字段；性别注册后永久锁定，不可自助修改。详见 5.1。
Q6 是否允许主动解除配对
允许。解除后配对失效、会话冻结为只读、双方移出彼此卡池与广场、不可再发消息，历史消息保留可查；已解除的两人不再互相推荐。详见 9.2。
Q7 聊天中发联系方式是否拦截
不拦截，仅对发送者提示一次。但公开资料（关于我 / 期待的他 / 兴趣介绍）中的联系方式仍拦截——那里对所有人可见，属于公开导流。详见 12.5。
Q8 年龄造假如何应对
本期不应对：只依赖用户自填的出生年月日，不引入实名认证与活体检测。仅保留「未成年 / 年龄不实」举报类型作为人工兜底。详见 14.3。
Q9 每日额度重置时区
北京时间（UTC+8），全站统一。服务端以 UTC 存储、按北京时间判定日期边界。详见 8.1。

20.3 其余非阻塞的小项

不影响开工，实现时顺手定即可
划卡是否允许撤回上一次滑动 体验
建议给「每日 1 次撤回」，作为误触的补救。若实现成本高可先不做（滑动已设阈值防误触）。详见 8.2。
被 Pass 的人是否要在广场中继续可见 体验
建议 Pass 后不再出现在任何通道（含广场），与卡池保持一致。

21里程碑与排期

里程碑周期交付内容验收标准
M1 账号与画像2 周 注册登录、Onboarding 五步（本人画像 / 兴趣 / 关于我 / 伴侣画像 / 期待的他）、资料完整度、个人中心资料编辑 新用户可完成注册并走完五步（不可跳过，含三段文字）；未走完无法进入划卡
M2 发现与配对2.5 周 划卡（浏览不限量 + 每日 10 次 Like 额度）、额度系统、Like/Pass、双向配对、谁喜欢我 / 谁看过我、恋爱广场检索 两个账号可跑通「划卡 → 双向 Like → 配对」
M3 聊天2 周 配对自动建会话、消息收发（文字/图片）、会话列表、未读数、WebSocket 实时通道、离线消息 配对双方可实时聊天
M4 相册与安全2 周 九宫格相册（上传/删除/拖拽排序/主图）、内容审核接入、举报与拉黑、风控限流 相册可拖拽排序；举报与拉黑生效
M5 体验打磨与压测1.5 周 推送、异常兜底、空态引导、曝光公平性调控、性能压测 核心接口达标，异常路径全部覆盖

合计约 10 周。M1 与 M2 之间有一个硬前置：需要先确定 Q1～Q4（额度口径、广场额度、是否付费、回 Like 额度），这四个问题直接决定 M2 的数据模型与接口形态，后改代价大。

建议的推进方式

M2 结束时做一次双人真机走查：用两个真实账号从注册一路走到聊天，把每个空态、每个错误提示都过一遍。交友产品的体验问题几乎都藏在「不合预期」的路径里——比如卡池空了、Like 了没人回应、配对后对方不说话。这些路径走一遍，比多看十页 PRD 有用。
