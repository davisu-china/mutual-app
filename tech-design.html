01技术选型总览

层选型理由
前端框架 React 18 + TypeScript + Vite 生态最成熟；Vite 冷启动快；TS 保障接口契约
UI 组件 shadcn/ui（Radix + Tailwind） 源码直接进项目、可任意改样式（不是黑盒依赖）；Radix 的无障碍与键盘交互是现成的
动效 Motion（原 Framer Motion） 「丝滑」的主要来源；布局动画、弹簧缓动、手势、手势中断都是开箱即用
数据请求 TanStack Query 缓存、去重、乐观更新、无限滚动；划卡场景全靠乐观更新保证「点下去立刻有反应」
轻状态 Zustand 体量小、无 Provider 嵌套；只放 UI 状态（当前卡片、弹层）
表单 react-hook-form + zod Onboarding 五步字段多，非受控表单性能好；zod 与后端校验规则共用一份 schema 定义
后端语言 Go 1.22+ 并发模型适合 WebSocket 长连接；部署为单二进制；团队可维护性好
Web 框架 Gin 生态最成熟、中间件多、文档全。备选 chi（更贴近标准库，无框架侵入）
数据访问 sqlc + pgx 从我们已有的 schema.sql 直接生成类型安全的 Go 代码；SQL 完全可见可控，复杂查询（卡池过滤、广场检索）不会被 ORM 藏起来
缓存 / 计数 Redis 7 额度缓存、限流、在线状态、WebSocket 多实例广播
对象存储 MinIO 照片与头像；预签名直传，不经过后端
检索 Elasticsearch P1 广场十几个筛选维度，PG 组合索引扛不住。MVP 可先用 PG，维度变多后再引入
两个关键选型判断

1. 用 sqlc 而不是 GORM。我们已经有 schema.sql，sqlc 能直接吃这份 DDL 生成类型安全的查询代码。更重要的是：本项目的核心查询（卡池候选过滤、广场多条件检索）逻辑复杂，SQL 必须可见、可调、可 explain——ORM 把这些藏起来，性能出问题时很难查。

2. 动效不是「加个 transition」。「丝滑」是个工程问题：需要乐观更新（点击瞬间就反馈，不等服务端）、布局动画（卡片自动补位）、图片预加载（下一张已经就绪）三件事一起做。只做 CSS transition 是出不来「丝滑」的，见第 6 章。

设计要点

  • 卡片栈三层：当前卡 + 后面两张（缩小 4.5% / 9%、下移 13 / 26px、透明度降至 62% / 32%）。有纵深，用户知道「后面还有人」。
  • 信息优先级：大图 → 昵称/年龄/城市 → 职业学历 → 兴趣标签。距离放在图片右上角，因为它是决策的硬条件之一，但不需要占正文位置。
  • 标签分两类：兴趣用品牌色（正向、可点进详情），客观条件（不抽烟、独生）用中性灰——避免整张卡都是红的。
  • 只有两个按钮：✕ 与 ♥。点卡片本身进详情（同时记一次 Visit），所以不需要第三个「详情」按钮。
  • ♥ 比 ✕ 大 8px 且带品牌渐变与光晕——视觉权重明确偏向「喜欢」，但 ✕ 依然够大够好点（56px 满足拇指热区）。

5.2 配对成功 · 最高光时刻

这一屏值得单独设计

配对是整个产品情感浓度最高的瞬间——用户等了很久、付出了 10 次额度中的一次，终于双向确认。这一屏如果只是一句冷冰冰的 toast，产品的「爽感」就丢了。

  • 全屏遮罩 + 深色底：把用户从浏览状态里抽离出来，形成仪式感。
  • 两个头像从左右飞入、在中间相撞，撞出心形与径向光晕（450ms 弹簧缓动）。
  • 轻微的设备震动反馈（H5 用 navigator.vibrate，App 用原生 haptic）。
  • 主按钮直达聊天，次要按钮留在原地——给「先打完这批卡再聊」的用户留出口。
  • 文案不用「匹配成功」这种机器词，用「你们互相喜欢」——说人话。
克制提醒

这一屏不要撒花瓣、不要放烟花、不要循环动画。一次清脆的相遇比一场嘈杂的庆典更符合「认真交往」的定位。动效跑完就停，别一直转。

设计要点

  • 「回喜欢」是列表内的一级动作，不要求点进主页再操作——这个页面的转化率最高，路径必须最短。

06交互与动效规范

「丝滑」= 三件事一起做，缺一不可

① 乐观更新：点击 Like 的瞬间就播动画、卡片就飞走，不等服务端返回。失败再回滚并提示。用户感知到的延迟是 0。

② 布局动画：卡片飞走后，后面的卡片要自动「补位」到前台（缩放与位移同步补间），而不是瞬间跳变。

③ 预加载：下一张卡的图片在用户看当前卡时就已经下载好了。图片没到位，动画再顺也会在换图时卡一下。

只做 CSS transition 是出不来丝滑的——上面三条里只有第 ② 条沾边。

6.1 动效时长与缓动

场景时长缓动说明
按钮按下120msease-outscale(0.96)，松手回弹
卡片飞出280mscubic-bezier(.22,1,.36,1)向对应方向位移 + 淡出 + 轻微旋转
卡片补位320msspring(stiffness 260, damping 26)由布局动画自动补间，不手写
页面切换220msease-out横向滑入 + 淡入；Tab 之间不转场
配对成功450msspring(stiffness 200, damping 20)头像飞入相撞 + 光晕扩散
弹层出现200msease-out背景淡入 + 内容上移 12px

总原则：动效服务于反馈，不是装饰。超过 400ms 的动画会让人觉得卡。除配对成功外，所有动效控制在 350ms 以内。

6.2 必须做好的几个微交互

交互行为
Like 按钮按下按钮缩放回弹 + 一圈光晕扩散 + 字符 ♥ 轻微放大 → 卡片随即飞出。按下就有反馈，不等松开
卡片进场新卡片从栈底位置自然顶到前台（布局动画），不重新挂载、不闪白
额度耗尽♥ 按钮变为禁用态并轻微抖动一次，同时底部滑出提示条说明「明日 00:00 恢复」，不做弹窗打断
图片加载blurhash 模糊占位 → 原图淡入（200ms），绝不出现空白或跳动
长列表滚动虚拟列表 + 惯性滚动；图片懒加载；滚动时暂停不必要的动画
下拉刷新仅在广场与消息列表启用；位移阻尼
错误恢复内联错误条 + 「重试」按钮，不用 alert 弹窗

6.3 骨架屏（不是 Loading 转圈）

卡片区、列表区、聊天区一律用骨架屏，形状与真实内容一致。加载超过 300ms 才显示骨架（避免闪烁），超过 5s 显示重试。

6.4 无障碍（Radix 顺手就能做到，别浪费）

  • 所有按钮有明确的 aria-label（✕ 读作「跳过」，♥ 读作「喜欢」）。
  • 键盘可用：← 跳过、→ 喜欢、Enter 进详情——这正好是按钮方案的天然优势。
  • 焦点环保留（不要 outline:none），颜色用品牌色。
  • 尊重 prefers-reduced-motion：关闭动画时降级为淡入淡出。

07为什么用按钮而不是滑动

这不是一个审美偏好，而是一个有明确理由的产品决策。我把理由记在这里，避免以后有人「顺手加回滑动」。

维度左右滑动按钮点击
桌面端 鼠标拖拽体验极差，用户根本不会用；且与文本选择、图片拖拽冲突 天然跨端，鼠标点击、触屏点按、键盘方向键都成立
误触率 滑动阈值难调：太灵敏会误划，太迟钝会觉得「划不动」；且滑动中途松手的状态需要额外处理 意图明确，按下才算数，几乎没有歧义
可访问性 屏幕阅读器与运动障碍用户基本无法使用 键盘、读屏都能覆盖
可测试性 手势难以自动化测试 点击是最容易写端到端测试的交互
可发现性 新用户需要被教育「要左右滑」 按钮就在那里，无需教育
实现时的一个硬约束

既然定了按钮方案，就不要再保留滑动手势作为「隐藏功能」。两套交互并存会导致：用户以为卡片能拖（拖了没反应或动了但没生效）、手势与页面滚动冲突、动画状态机复杂化。要做就只做按钮。

PRD 3.3 规定五步全部不可跳过。这个约束必须在后端中间件实现——前端拦截只是体验，后端拦截才是规则。OnboardGuard 挂载在划卡、广场、聊天等路由组上，users.onboarded_at IS NULL 则返回 403 ONBOARDING_REQUIRED，前端据此跳转向导。只做前端拦截，用户改个请求就能绕过。

8.2 并发与幂等（本项目最容易出错的地方）

场景处理方式
扣额度（防超额） 条件更新，靠 affected rows 判断：
UPDATE daily_quotas SET used_like_count = used_like_count + 1
  WHERE user_id=$1 AND quota_date=$2 AND used_like_count < limit_count
返回 0 行 = 额度已满，回滚并返回业务错误码。不要先 SELECT 再 UPDATE——那样并发下一定超额
重复 Like user_actions 有 (from_user,to_user,action) 唯一约束，ON CONFLICT DO NOTHING
双方同时 Like INSERT ... ON CONFLICT (user_a,user_b) DO NOTHING，以 affected rows 判断「本次是否真的配对成功」，只有真正插入成功的那一次才创建会话、发配对通知。否则两边都会弹配对动画、建出两个会话
额度重置的日期 应用层按北京时间计算（time.Now().In(shanghai).Format("2006-01-02")），严禁用 CURRENT_DATE——服务器跑 UTC 时，会在北京时间早上 8 点前后算错一天
消息重发 messages 的 (conversation_id, client_msg_id) 唯一约束兜底

8.3 事务边界示例（Like 全流程）

// service/action.go —— 一个事务里做完四件事
func (s *ActionService) Like(ctx, fromID, toID int64, source string) (*Result, error) {
    return s.tx.WithTx(ctx, func(q *repo.Queries) (*Result, error) {
        day := time.Now().In(shanghaiTZ).Format("2006-01-02")   // ← 北京时间

        // 1. 扣额度（条件更新，0 行即失败）
        n, err := q.ConsumeQuota(ctx, fromID, day)
        if err != nil { return nil, err }
        if n == 0 { return nil, ErrQuotaExhausted }

        // 2. 写 Like（重复则忽略）
        q.UpsertAction(ctx, fromID, toID, "like", source)

        // 3. 判配对：只有真正插入成功才算配对
        a, b := order(fromID, toID)          // 规范化 user_a < user_b
        matched := q.TryCreateMatch(ctx, a, b) > 0

        // 4. 配对成功才建会话
        if matched { q.CreateConversation(ctx, a, b) }
        return &Result{Matched: matched}, nil
    })
}

配对成功后的事务外动作（发通知、推 WebSocket 消息）用 Outbox 模式：事件先落库，再由投递器异步推送，保证「不全丢、可重放」。

09数据存储设计

9.1 PostgreSQL

表结构见仓库根目录的 schema.sql（16 张表）。这里只补充工程实现要点：

  • 迁移用 golang-migrate，禁止手改线上表结构。
  • 连接池用 pgxpool，max_conns 按 CPU 核数 × 2 + 磁盘数 设，并设置 MaxConnLifetime 避免僵死连接。
  • 所有对 user_profiles 的读写走同一套可见性规则（PRD 第 15 章）：收入、公司、体重、养老压力这几个字段有 *_public 开关，序列化时必须按「看的人是谁」决定是否输出，不能图省事全查出来。
  • 曝光统计（exposure_stats）用异步累加：请求时只写 Redis 计数器，定时任务批量落库，避免每次划卡都写一次统计表。

10.4 曝光均衡（决定生态健康）

推荐排序里加一项曝光修正分：− k × 该用户近 7 天曝光量，并对新注册用户给 72 小时加权。没有这一项，头部的少数人会吃掉绝大部分 Like，其余用户长期零配对后流失，卡池随之萎缩。

  • 密码 bcrypt(cost 12) 或 argon2id；登录失败统一话术，不泄露手机号是否存在。
  • MinIO bucket 全私有，只走预签名 URL。
